## Design Specificity Verdict

**LLM assessment**: Authored for Overlap, not a reskin — the `DIRECTION_CONTRACT` audit trail in `app/layout.tsx`, the documented No-Kicker Rule (with its own recorded failure/revert story), the deliberate corkboard-style asymmetric landing steps, and a calm, specific copy voice all point to real authorship. Two things undercut it: `CalendarGrid` is a flat agenda list with no time axis or grid — for an app whose entire premise is "see everyone's week merged," it currently reads as a generic to-do feed with dates; and the wordmark has two inconsistent treatments across screens (NavBar's correct Label style vs. login/landing's different size and tracking).

**Deterministic scan**: Clean outside one file. 3 findings, all `design-system-font-size` (advisory), all in `app/global-error.tsx` (lines 47, 61, 82) — flagging `1.5rem`/`0.875rem` as off the DESIGN.md type ramp. Likely a justified exception: that file is a Next.js `global-error.tsx` boundary deliberately built with inline-styles-only so it survives even if the app's own CSS pipeline is what's broken — it structurally can't reference the design tokens.

Notably, the detector did not catch the wordmark inconsistency Assessment A found — its font-size rule appears scoped to inline `style={{fontSize}}` usage, not Tailwind utility classes like `text-sm` vs `text-xs`. That's the clearest example in this run of the LLM review catching a real token-drift issue the mechanical scan structurally can't see.

**Visual overlays**: Unavailable. No browser-automation tool was exposed in either subagent's session, and the app can't render its logged-out landing page without live `DATABASE_URL`/Google OAuth credentials (confirmed: `npm run dev` 500s at module load in `db/client.ts`). Both reviews are source-grounded; no `[Human]` tab overlay exists.

## Overall Impression

The design system is unusually disciplined for a small personal project — one accent, two radius steps, a documented and enforced pending-state primitive, accessible error boundaries. But the system breaks down at exactly the two moments that matter most: the merged calendar view (the product's actual reason to exist) is a plain list rather than something that shows the shape of a day, and the highest-trust actions (share/unfriend) drop out of the entire design language into a bare OS `confirm()` dialog.

## What's Working

1. **`SubmitButton` as systemic infrastructure** — every server-action button gets `aria-busy`, disabled-during-pending, and a contextual spinner label for free, almost everywhere.
2. **Accessible, resilient error boundaries** — `global-error.tsx` deliberately avoids any CSS dependency, and both boundaries move focus to the heading on mount.
3. **Copy discipline** — empty/zero states name the actual condition and suggest a next step rather than bare "No results."

## Priority Issues

**[P0] Native `window.confirm()` breaks the design system at the highest-trust moments**
- Why it matters: `ConfirmSubmitButton` uses the browser's native dialog for "Share calendar" and "Remove friend" — the two actions PRODUCT.md says must "not feel casual or accidental."
- Fix: Replace with an in-system confirmation built from the existing card/pill vocabulary, preserving accessible focus-trap/Escape behavior.
- Suggested command: /impeccable harden

**[P1] The merged view doesn't visualize a calendar**
- Why it matters: `CalendarGrid` is a flat, day-grouped list — no time axis, no visual sense of gaps/overlaps, for a product whose premise is "see everyone's week merged."
- Fix: Introduce a lightweight time-proportional layout per day.
- Suggested command: /impeccable layout

**[P1] Wordmark has two inconsistent treatments**
- Why it matters: DESIGN.md reserves the Label style for "exactly one use" and documents a prior near-miss on this exact surface; login/landing diverge from NavBar.
- Fix: Apply the Label treatment identically everywhere.
- Suggested command: /impeccable polish

**[P2] No bulk/saved-group actions for a recurring core task**
- Why it matters: `find-time` requires re-selecting the same friends every visit despite this being a repeated task per PRODUCT.md.
- Fix: Persist last-used friend selection as the default.
- Suggested command: /impeccable optimize

**[P2] Share confirmation doesn't disclose the all-future-friends constraint**
- Why it matters: Sharing silently includes any friend added later, with no re-confirmation at that moment either.
- Fix: Add one clause to the confirmation copy about future friends.
- Suggested command: /impeccable clarify

## Persona Red Flags

**Jordan (First-Timer)**: Reads "Choose which calendars friends can see" and assumes per-friend control exists; the all-or-nothing reality isn't disclosed until after sharing. The native `confirm()` dialog reads as the app "breaking."

**Sam (Accessibility-Dependent)**: Toggle buttons correctly use `aria-pressed`; checkboxes are real labeled inputs. Gap: Show/Hide friend action produces no `aria-live` confirmation beyond the button's own label flip.

**Dana (project-specific — the friend on the receiving end)**: No notification path exists for the passive side of a share/unfriend action; events silently stop appearing with no explanation.

## Minor Observations

- `FindTimeForm`'s submit button is hand-coded instead of routing through `SubmitButton`.
- The Show/Hide friend toggle relies on a dashed-vs-solid border as its sole visual cue.
- `ReconnectBanner` has no dismiss/snooze.
- `find-time`'s duration field is a raw number spinner rather than common presets.
- Detector's 3 `design-system-font-size` findings in `global-error.tsx` are a defensible architectural exception, not a real defect.

## Questions to Consider

1. If "Find a time" already computes gaps precisely, why does the merged view show none of that visually?
2. The confirmation copy is well-written — so why deliver it through a generic browser dialog?
3. Is silence about the all-future-friends sharing scope really intended, or an inherited oversight?
